# Architecture Decision Records (ADR)

Append-only log. Format per entry:

```
## ADR-NNNN: <title>
Date: YYYY-MM-DD · Status: Accepted | Superseded by ADR-XXXX
Context: <the problem/forces>
Decision: <what we chose>
Consequences: <what this binds us to>
```

Agents must not contradict an Accepted ADR; to change one, write a new ADR that supersedes it.

---

## ADR-0001: Clean Architecture + DDD with CQRS/MediatR on .NET 10
Date: 2026-07-11 · Status: Accepted
Context: docs/3. mandates strict layering for an 8-month, 4-phase build with parallel AI agents; parsers/engines must stay testable and swappable.
Decision: Four projects (Domain / Application / Infrastructure / WebApi); CQRS via MediatR; FluentValidation in Application; EF Core 10 + MSSQL in Infrastructure only. CPM/EVM engines are pure Application services.
Consequences: More boilerplate per feature, but agents can work in parallel without layer conflicts; engines unit-test without DB.

## ADR-0002: Multi-tenant isolation via TenantId + EF global query filters
Date: 2026-07-11 · Status: Accepted
Context: docs/4. specifies multi-tenant SaaS; cross-tenant leakage of contract/payment data is the worst-case security failure.
Decision: Every tenant-owned table carries `TenantId` (indexed, leading column of composite indexes); a global EF query filter bound to `ITenantProvider` applies on all reads; writes stamp TenantId server-side, never from client input.
Consequences: Single database, simple ops; security-auditor treats any unfiltered query as release-blocking; admin cross-tenant tooling needs explicit filter bypass with audit.

## ADR-0003: MS Project integration via MSPDI XML (MPXJ), never binary .MPP or interop
Date: 2026-07-11 · Status: Accepted
Context: docs/วิเคราะห์ฯ §2 — binary .MPP parsing/interop is unstable and slow in cloud containers.
Decision: Import/export MS Project data through MSPDI XML using MPXJ.Net; XER parsed natively (tab-delimited %T tables); Excel via EPPlus.
Consequences: Users export .mpp → MSPDI when needed; XML hardening (XXE, size caps) is mandatory on the import path.

## ADR-0004: Virtualized rendering for Gantt and large tables
Date: 2026-07-11 · Status: Accepted
Context: docs/2. risk #1 — browser performance with 10,000+ activities is a High risk.
Decision: react-window-style row virtualization for all large lists and the Gantt; bars drawn on a canvas/single-SVG layer; heavy series computation in Web Workers.
Consequences: Gantt components must keep row props stable/memoized; no DOM-per-bar designs will pass review.

## ADR-0005: Offline-first site modules via IndexedDB outbox + Background Sync
Date: 2026-07-11 · Status: Accepted
Context: docs/1. §5 and docs/2. risk #3 — site connectivity is unreliable; photo/weather/progress capture must not block on network.
Decision: Site-facing writes enqueue into an IndexedDB outbox (client-compressed photos included) and flush via Service Worker Background Sync; server wins on schedule data, last-write-wins + audit on site logs.
Consequences: Every site-module feature ships with offline tests; sync status must be visible in the UI.

## ADR-0007: EAC is a selectable variant computed by one Performance-Factor engine — five variants in the engine, three in the v1 UI
Date: 2026-07-27 · Status: Accepted
Context: Two upstream artifacts written in parallel diverged. `docs/specs/master-plan/backlog-detailed.md` (§1, US-7.2) scoped a 3-value enum `Project.DefaultEacVariant` (`BacOverCpi`/`Atypical`/`Combined`) with a dropdown showing exactly those three. `docs/specs/master-plan/domain-decisions.md` §1 formalised **five** variants (`CpiBased`/`Atypical`/`CpiSpiBased`/`BottomUpEtc`/`CustomPf`) as one unified engine $ETC = PF\times(BAC-EV)$, recommended `Project.EacVariantDefault` + `EacCustomPerformanceFactor` + `EacManualEtc`, and recommended returning every computable variant per response. The engine cost of all five is negligible ("five multiplications on four scalars") and the edge-case matrix, invariants and fixtures (A1–A5, D1–D3, E–I) are already written. The real cost of the two extra variants is **UI**: `BottomUpEtc` and `CustomPf` each need a persisted project input, validation, permissioning and user guidance.
Decision: (a) The **engine implements all five variants** from Sprint 7 as a single pure Application service using the unified PF form; there is no per-formula code branch. (b) `GET /api/v1/projects/{id}/evm` returns **every computable variant** with an explicit `null` + machine-readable reason (`NotStarted`/`NoActualCost`/`NoPlannedValue`/`ZeroCpi`) for the rest, plus `selectedVariant`. (c) Field naming follows domain-expert: `Project.EacVariantDefault` (enum, NOT NULL, default `CpiBased`), `Project.EacCustomPerformanceFactor decimal(9,4) NULL` (> 0), `Project.EacManualEtc decimal(18,2) NULL` (≥ 0). po-analyst's `Project.DefaultEacVariant` and the values `BacOverCpi`/`Combined` are **superseded**; the mapping is `BacOverCpi` → `CpiBased`, `Combined` → `CpiSpiBased`. (d) The **v1 UI (Sprint 7) surfaces only the three index-based variants** in the selector; `BottomUpEtc`/`CustomPf` are computed and returned but their input UI lands in Sprint 14. (e) EAC is never persisted on `Project` — only inside immutable `EvmPeriodSnapshot` rows together with the variant and the PF actually used. (f) Changing `EacVariantDefault` is a mutating domain operation (audit log) restricted to PM/QS/Executive — this closes backlog open question D4 as an architecture decision, not a domain one.
Consequences: One engine, one test suite; adding a variant to the UI later is a frontend-only change. QA must cover all five variants and the edge matrix from Sprint 7, not just the three shown. The frontend must never assume a fixed EAC ordering when colour-coding (ordering reverses when CPI > 1). Any golden-file EAC comparison against P6 is invalid until the source project's actual P6 Earned Value setting is confirmed (risk R-01 in `docs/10.`).

## ADR-0008: Approval authority is an amount-tiered, version-pinned policy engine built from Sprint 2 (not a role-only boolean matrix)
Date: 2026-07-27 · Status: Accepted
Context: Second parallel divergence. `backlog-detailed.md` scoped `ApprovalMatrixEntry(TenantId, Module, Role, CanApprove)` — a per-role boolean — landing Sprint 2 (model) / Sprint 9 (admin UI) / Sprint 10 (VO reuse). `domain-decisions.md` §3 and `.claude/knowledge/domain/approval-workflow.md` §5 argue for an amount-tiered `ApprovalPolicy` / `ApprovalPolicyRule` / `ApprovalAction` model, because a role-only matrix cannot express the single most common real DoA rule ("PM approves VOs under ฿500,000; above that the Project Director must also sign") and would force per-tenant code branches. The choice is build-simple-then-migrate versus build-rich-now. Build-then-migrate is not a cheap path here: the boolean check is a *different call shape* from a multi-step chain (chain snapshot, `StepNo` pointer, `RevisionNo`, quorum, self-approval rules), so the enforcement hook, the write API, the admin UI and their tests would all be discarded — and the data to migrate is approval history, i.e. legal evidence, which must never be rewritten in place. Meanwhile the rich model has **no remaining design work**: the routing algorithm (§5.3), the state machines (§4) and fixtures R1–R10 are fully specified.
Decision: Build the amount-tiered model directly, starting Sprint 2. `ApprovalMatrixEntry` is superseded and must not be created. A role-only DoA is expressed as a single-step rule spanning `[0.00, NULL)` — the simple case is a *configuration* of the rich model, never a second code path. `User.Role` gains `ProjectDirector` (required for a 3-tier chain; adding it at Sprint 2 is free, later it is a claims/enum migration). Surface is staged to keep Sprint 2 bounded: **Sprint 2** = the three tables + seeded `TH-Default-VO`/`TH-Default-IPC` policies + a pure `IApprovalRoutingService` (fail-closed, version-pinned) + read-only `GET /api/v1/tenants/{id}/approval-policies`; **Sprint 9** = Payment Certificate state machine, policy write API, Tenant Admin policy editor UI; **Sprint 10** = VO chain + cumulative-VO escalation; **Sprint 15** = policy version history + routing simulator. Schema-present but deliberately not surfaced in v1: `RequiredUserId`, `QuorumCount > 1`, project-scoped policy override (`ApprovalPolicy.ProjectId`), delegation (out of scope entirely).
Consequences: Sprint 2 grows by one table-set plus a routing service; Sprints 9 and 10 shrink correspondingly and carry no rework. `ApprovalAction` is append-only legal evidence — corrections are compensating rows, never edits or migrations. Every approve/reject endpoint resolves the chain server-side, tenant-scoped (ADR-0002); an empty chain fails closed with `ApprovalPolicyGap` (422) and must never auto-approve. Policy edits create `Version+1`; in-flight documents keep the version that routed them. `security-auditor` must review the policy endpoints and routing before Sprint 9 close and before Sprint 10 close — not only at Sprint 15.

## ADR-0009: `ActivityProgressLog` is the system of record for progress over time; historical EVM reads the latest dated snapshot as of $t$; closed periods are frozen in `EvmPeriodSnapshot`
Date: 2026-07-27 · Status: Accepted
Context: `docs/9.` §4 stores only `Activity.ProgressPercentage`, overwritten in place, so historical PV/EV could only be reconstructed by parsing `AuditLog.BeforeJson/AfterJson` — fragile and unfit for a reporting engine. `backlog-detailed.md` §2.2 introduced an append-only `ActivityProgressLog` and raised open question D1 (what the historical reconstruction rule should be). `domain-decisions.md` was produced in parallel and never saw the new entity, so D1 was never answered. This is a data-modelling decision, not a formula question.
Decision: `ActivityProgressLog` (append-only, immutable, same pattern as Weather Log) is authoritative for progress over time. Reconstruction is a **step function, no interpolation**: $Pct_i(t)$ = the `ProgressPercentage` of the entry for activity $i$ with the greatest `PeriodEndDate` ≤ $t$ (ties broken by greatest `RecordedAt`); an activity with no entry ≤ $t$ contributes 0. $EV(t) = \sum_i BudgetCost_i \times Pct_i(t)/100$. `Activity.ProgressPercentage` is a **denormalised cache** of the entry with the greatest `PeriodEndDate`; a backdated correction is appended and does **not** move the cache. Every write path (batch grid, Excel import, offline sync, photo-linked update) writes a log row; no path writes the cache directly. Derived series legitimately change when a backdated entry lands — that is correct and fully audited because the log is append-only — so **closed reporting periods are frozen** in an immutable `EvmPeriodSnapshot` (data date, BAC, PV, EV, AC, EAC variant + PF used) which is what dashboards, exported PDFs and payment certificates cite for past periods. Closes backlog open question D1.
Consequences: mandatory index `(TenantId, ActivityId, PeriodEndDate DESC)` plus `(TenantId, PeriodEndDate)` for period rollups; `database-engineer` must watch row volume (10,000 activities × weekly for 8 months ≈ 350k rows/project — see risk R-11). QA owns an out-of-order backfill fixture from Sprint 1. Reports that must be reproducible cite a snapshot id, never a live recomputation.

## ADR-0010: Cloud-agnostic containerization with the AWS-vs-Azure decision deferred to an explicit gate inside Sprint 16
Date: 2026-07-27 · Status: Accepted
Context: `docs/9.` §11 item 5 (AWS ECS vs Azure Container Apps) was deliberately deferred by the human. Waiting for the answer would stall all infrastructure work until Phase 4; guessing risks rewriting the deployment path and any provider SDK usage that leaks into application code.
Decision: Make provider choice a late, cheap decision. (a) **From Phase 0**: multi-stage Dockerfiles (API and web), a `docker-compose` stack (api + web + MSSQL + object storage) that is the same topology as production, configuration exclusively via environment variables, and `/health/live` + `/health/ready` endpoints. (b) **From Sprint 1**: generic CI — build → test → lint → security scan (vulnerable NuGet/npm packages, image scan) → push an OCI image tagged by commit SHA to an OCI-compatible registry (GHCR by default). (c) **No provider SDK in application code**: object storage sits behind `IFileStorage` in Infrastructure with a local/S3-API-compatible adapter for dev and staging; the provider adapter is written only after the gate. Secrets come from `IConfiguration`/env only. EF migrations are emitted as an idempotent SQL script artifact applied by a separate, human-approved job. (d) **Sprint 16 is split**: *16A* a provider-agnostic staging deployment (compose or single-node k3s) that satisfies US-16.1's human sign-off gate; *16B* an explicit **decision gate** — the human picks AWS ECS Fargate or Azure Container Apps — followed by execution of the matching ready-written runbook. If the gate is not passed by the end of Sprint 15, 16A still completes and production deployment becomes a separately scheduled runbook execution; the 16-sprint timeline is not blocked.
Consequences: No provider-specific managed service (queues, functions, provider-native identity) may be introduced before the gate without a superseding ADR. The only provider-specific code is the storage/secrets/telemetry adapter set, isolated in Infrastructure. Staging must stay functionally equivalent to the production topology so the gate changes a deployment target, not an architecture. Both runbooks live in `docs/10.` §13 and must be kept executable.

## ADR-0011: MSPDI parsing ships an interim hand-written reader behind `IMspdiScheduleParser`; MPXJ.Net is not currently buildable on this toolchain
Date: 2026-07-29 · Status: Accepted (interim; revisit when the upstream defect is fixed)
Context: ADR-0003 specifies MPXJ.Net for MSPDI parsing. Adding `PackageReference Include="MPXJ.Net"` (tried: 13.0.0, 16.5.0 — the oldest and newest available) fails `dotnet build` unconditionally, before any application code compiles. Root cause independently reproduced twice — once by `backend-developer` inside the real solution, once by the orchestrator in an isolated scratch console project with no other dependencies — narrowing it to MPXJ.Net's own transitive dependency chain, not this repo's configuration: `IKVM.Util.Jar.JarFileUtil.GetModuleNameAndVersionFromFileName` throws `ArgumentOutOfRangeException: count ('1') must be less than or equal to '0'` while IKVM.Maven.Sdk transpiles MPXJ's Java dependency graph, specifically on `commons-codec-1.15.jar`. That jar was checked directly (`file` + magic-byte inspection: a valid, uncorrupted JAR/ZIP, 353,793 bytes, standard Maven Central artifact) — the defect is in IKVM's own filename-parsing logic for this jar's name shape, not a bad download. Reproduced identically across IKVM 8.7.5, 8.14.0, and 8.15.0 (three versions spanning the full currently-published range) paired with both tried MPXJ.Net versions — six failing combinations, zero succeeding. Network access to both Maven Central and NuGet was confirmed working, ruling out a connectivity/proxy explanation. Because `commons-codec` is a foundational, rarely-bumped transitive dependency reachable from MPXJ.Net's Java side (via Apache POI) regardless of which MPXJ.Net version is selected, and NuGet/Maven dependency resolution is deterministic, this is expected to reproduce identically in CI/Docker or any other build environment — it is a genuine, currently-unpatched upstream defect in the IKVM/MPXJ.Net toolchain combination, not an artifact of this sandbox.
Decision: Ship Sprint 3 with a hand-written `MspdiScheduleParser` (`backend/src/CMPlus.Infrastructure/Parsers/Mspdi/`) reading the MSPDI XML schema directly, hardened against XXE the same way any untrusted XML input in this codebase must be (`DtdProcessing.Prohibit`, `XmlResolver = null`). It sits behind `IMspdiScheduleParser` (`backend/src/CMPlus.Application/Abstractions/`), the exact seam MPXJ.Net would occupy, so adopting the real library later — once IKVM fixes this upstream, or MPXJ.Net bumps past the affected commons-codec version — is a single-file swap with zero ripple into Application/WebApi/tests. ADR-0003's actual intent (never binary `.mpp`/COM interop) is fully preserved; only the specific library named in that ADR is deferred. This ADR does not reopen or contradict ADR-0003 — it records why its named implementation isn't in place yet and what closes the gap.
Consequences: The interim parser has no upstream Java-side test corpus behind it — its golden-file coverage is only as good as the hand-built, spec-compliant fixtures `backend-developer`/`qa-engineer` authored this sprint (see the fixture-provenance note in `backend/tests/fixtures/goldenfiles/`), not verified against real MS Project output. `devops-engineer` should re-attempt `MPXJ.Net` in the actual CI/Docker build image opportunistically (e.g. when bumping any related package) to check whether an upstream fix landed, but should not expect a different outcome merely from a different machine. Any future attempt must re-run this same isolated-repro check before assuming the fix is real. No other parser (XER, Excel) is affected — this is specific to the Java-interop path only.
