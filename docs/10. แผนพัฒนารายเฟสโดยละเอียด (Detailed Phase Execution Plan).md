## 2. ผลการประสาน artifact ต้นน้ำ (Reconciliation)

artifact ทั้งสองถูกผลิตขนานกันโดยไม่เห็นกันและกัน จึงมี 2 จุดขัดแย้งจริง และ 2 คำถามค้าง

### 2.1 EAC — engine 5 variant, UI v1 แสดง 3 (ADR-0007)

| ประเด็น | po-analyst (backlog §1, US-7.2) | domain-expert (§1) | **ข้อยุติ** |

และ `CustomPf` ต้องมีช่องกรอก `EacCustomPerformanceFactor` พร้อม validation, สิทธิ์, และคำอธิบาย
ให้ผู้ใช้เข้าใจว่าเมื่อไรควรใช้ — เป็นงาน UX ที่ไม่จำเป็นต่อ MVP ของ Sprint 7
จึงแยก **engine surface** ออกจาก **UI surface**

**ผลต่อการวางแผน:**
- **Sprint 7** — engine ครบ 5 variant + API ส่งครบ + selector บนหน้า EVM แสดงเฉพาะ 3 ตัวที่เป็น
  index-based (`CpiBased` [default], `Atypical`, `CpiSpiBased`)
- **Sprint 8** — Dashboard/PDF export ใช้ `EacVariantDefault` ของโครงการ พร้อมแสดงชื่อสูตรกำกับ
- **Sprint 14** — เปิด UI ของ `BottomUpEtc` / `CustomPf` (ช่องกรอกบน Project Info + ขยาย selector เป็น 5)
  วางไว้ที่นี่เพราะ bottom-up re-estimate เป็นงานคู่กับการ rebaseline/ปิดงวดใหญ่
- **การเปลี่ยน default ของโครงการ** = mutating operation → audit log, จำกัดสิทธิ์ PM/QS/Executive
  (**ปิดคำถาม D4** ของ backlog — เป็นการตัดสินใจเชิงสถาปัตยกรรม ไม่ต้องส่งกลับ domain-expert)

### 2.3 ปิดคำถาม D5 — advance-recovery mechanics ถูกตอบแล้ว

backlog เปิด **D5** ว่า "กลไกการหักคืนเงินล่วงหน้ายังไม่นิยาม — ด่วน บล็อก Sprint 9"
คำถามนี้ถูกเขียนโดยไม่เห็นผลงานขนานของ domain-expert ซึ่ง **ตอบไว้ครบแล้ว** ใน
`domain-decisions.md` §2.3 + fixture P1–P7 (§2.5):

- `Project.AdvanceRecoveryMethod enum { ProRata, ThresholdBanded, Manual }` **default `ProRata`**
- `ProRata` (ปฏิบัติไทย): $D_k = \frac{a}{100}G_k$ จำกัดด้วยยอดคงค้าง
- `ThresholdBanded` (FIDIC 14.2): เริ่มหักหลังผ่าน threshold $s$, อัตรา $\rho$ ของส่วนเกิน,
  บังคับหักหมดเมื่อถึง $e$ (default $s=10, \rho=25, e=90$) — fixture P6
- `Manual`: QS กรอกเอง ยังจำกัดด้วยยอดคงค้าง

**สถานะ: D5 = Resolved 2026-07-27 — ไม่ใช่คำถามค้างอีกต่อไป** Sprint 9 implement ครบทั้ง 3 วิธี
(engine เล็กมาก และ fixture มีครบ) ห้าม implement placeholder/TODO ตามที่ US-9.1 เคยอนุญาตไว้

พร้อมกันนี้ Sprint 9 ต้องรับ **ส่วนขยายที่ domain-expert เพิ่ม** ซึ่ง backlog ยังไม่รู้:
สูตร Net Payment ที่แก้แล้ว (หักบน **period gross** $G_k$ ไม่ใช่ cumulative),
`RetentionCapPercentage`, `ContractValue`, `ProjectFinanceLedger`,
`PaymentCertificate.{GrossCertifiedAmount, AdvanceRecoveryAmount, PreviousCumulativeApprovePct, RevisionNo}`
และกฎ **ปัดเศษ half-away-from-zero รายบรรทัด** (fixture P7 — `MidpointRounding.AwayFromZero`)

### 2.4 ปิดคำถาม D1 — การสร้าง PV/EV ย้อนหลัง (ADR-0009)

**ข้อยุติ (การตัดสินใจเชิงสถาปัตยกรรม/data modeling ไม่ใช่คำถาม domain):**

- `ActivityProgressLog` (append-only, immutable) = **system of record** ของความคืบหน้าตามเวลา
- การสร้างย้อนหลังเป็น **step function ไม่มี interpolation**:
  $Pct_i(t)$ = ค่าจาก entry ที่ `PeriodEndDate` มากที่สุดที่ $\le t$ (เท่ากันให้ใช้ `RecordedAt` ล่าสุด)
  ไม่มี entry $\le t$ → นับ 0 · $EV(t) = \sum_i BudgetCost_i \times Pct_i(t)/100$
- `Activity.ProgressPercentage` = **cache** ของ entry ที่ `PeriodEndDate` มากสุด;
  entry ย้อนหลัง (backdated) จะถูก append แต่ **ไม่** ขยับ cache
- ทุกเส้นทางเขียน (batch grid, Excel import, offline sync, photo-linked) **ต้องเขียนผ่าน log**
  ห้าม path ใดเขียน cache ตรง ๆ
- series ที่คำนวณสด **เปลี่ยนได้** เมื่อมี entry ย้อนหลังเข้ามา (ถูกต้องและตรวจสอบได้ เพราะ log
  เป็น append-only) ส่วน **งวดที่ปิดแล้วถูกแช่แข็ง** ใน `EvmPeriodSnapshot` (immutable: data date,
  BAC, PV, EV, AC, EAC variant + PF) ซึ่งเป็นสิ่งที่ dashboard/PDF/ใบรับรองอ้างอิงสำหรับงวดในอดีต

กฎ "ไม่เขียนทับประวัติ" ของ evm-formulas.md จึงถูกรักษาไว้อย่างเข้มงวดในระดับ **snapshot**
ขณะที่ derived series ยังสะท้อนข้อมูลที่ถูกแก้ให้ถูกต้องได้ — สองเรื่องนี้ต้องไม่สับสนกัน

## 4. วิธีอ่านตารางงาน (Conventions)

- **Task ID:** `S{sprint}-{DISC}-{n}` · `DISC` ∈ `BE` (backend-developer), `FE` (frontend-developer),
  `DB` (database-engineer), `QA` (qa-engineer), `DO` (devops-engineer), `SEC` (security-auditor)
  Phase 0 ใช้ prefix `P0-`
- **US:** เลข story ใน `backlog-detailed.md` · `*` = story ใหม่ที่เอกสารนี้เพิ่ม (po-analyst รับไป fold)
- **DoD:** ต้องวัดได้ (ตัวเลข, ชื่อ test, ค่าที่ต้องตรง) — ห้ามเขียน "ทำงานได้ถูกต้อง"
- **ขึ้นกับ:** Task ID ของ sprint ก่อนหน้า หรือ task ในสprintเดียวกัน
- แต่ละ sprint ปิดท้ายด้วย `/feature-pipeline`: `qa-engineer` → `code-reviewer` ∥ `security-auditor`
  (เมื่อเข้าเงื่อนไข §12) → `knowledge-curator`
- ระบุเฉพาะ discipline ที่ **ทำงานจริง** ใน sprint นั้น

### 13.3 Runbook A — AWS ECS Fargate (โครงร่างพร้อมใช้)

1. สร้าง ECR repository 2 ชุด (api, web) → ตั้ง CI ให้ push image เดิม (tag = SHA) เพิ่มไปยัง ECR
2. เครือข่าย: VPC + subnet สาธารณะ/ส่วนตัว + security group (เปิดเฉพาะ 443 จากภายนอก)
3. ฐานข้อมูล: RDS for SQL Server (Multi-AZ ตามความจำเป็น) + parameter group + สำรองข้อมูลอัตโนมัติ
4. ไฟล์: S3 bucket (บล็อก public access) → เขียน adapter `IFileStorage` ฝั่ง AWS (S16-DO-05)
5. Secrets: AWS Secrets Manager → ฉีดเป็น env var ของ task definition
6. Compute: ECS cluster + task definition (api, web) + service หลัง ALB + target group ที่ใช้ `/health/ready`
7. Observability: CloudWatch Logs + alarm บน 5xx/latency/CPU
8. Deploy: CD job อัปเดต service เป็น image tag ใหม่ (rolling) + งาน migration แยกที่ต้องอนุมัติ
9. ตรวจรับ: smoke test ผ่าน + ทดสอบ rollback กลับ tag เดิมสำเร็จ

### 13.4 Runbook B — Azure Container Apps (โครงร่างพร้อมใช้)

1. สร้าง Azure Container Registry → ตั้ง CI ให้ push image เดิม (tag = SHA) เพิ่มไปยัง ACR
2. เครือข่าย: Container Apps Environment + VNet integration + ingress ภายนอกเฉพาะ web/api ที่จำเป็น
3. ฐานข้อมูล: Azure SQL Database (หรือ SQL MI ถ้าต้องการฟีเจอร์ระดับ instance) + firewall/private endpoint + backup
4. ไฟล์: Azure Blob Storage (container แบบ private) → เขียน adapter `IFileStorage` ฝั่ง Azure (S16-DO-05)
5. Secrets: Azure Key Vault + managed identity → อ้างเป็น secret ของ Container App
6. Compute: Container App 2 ตัว (api, web) + revision + กฎ scale + health probe ที่ `/health/ready`
7. Observability: Application Insights + Log Analytics + alert rule
8. Deploy: CD job สร้าง revision ใหม่จาก image tag (traffic split ได้) + งาน migration แยกที่ต้องอนุมัติ
9. ตรวจรับ: smoke test ผ่าน + ทดสอบสลับ traffic กลับ revision เดิมสำเร็จ

### 13.5 สิ่งที่ **ห้าม** ทำก่อนผ่าน gate

- ใช้ managed service เฉพาะเจ้า (queue, function, provider-native identity) ในเส้นทางหลัก
- import SDK ของ provider เข้ามาใน `CMPlus.Application` หรือ `CMPlus.Domain`
- ผูก schema/พฤติกรรมกับฟีเจอร์เฉพาะของ SQL เวอร์ชันที่มีเฉพาะบางผู้ให้บริการ
การฝ่าฝืนต้องเขียน ADR ใหม่ที่ supersede ADR-0010 ก่อนเท่านั้น
